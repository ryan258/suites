# Project Bible

## What Is It

Ryan Project Suites is a local portfolio architecture, contract library, and evidence-backed
migration program. Its output is a small set of coherent product systems plus a preserved record of
where every retained capability came from. The control plane is a standard-library Python CLI and
human-readable JSON/Markdown, so it stays usable without a service, account, or network.

## Setting

It lives locally under `/Users/ryanjohnson/Projects/suites`, next to—but never silently inside—the
source repositories it governs. The aesthetic is calm operations: small commands, visible state,
plain files, explicit handoffs, and recovery paths.

## Tone

Direct, grounded, recoverable. It should say what exists, what is inferred, what is stale, and what
must happen next without pretending that plans are products.

## Format Rules

- Every suite has one promise, explicit anchors, member relationships, contracts, bounded waves,
  and evidence-based completion criteria.
- Every source directory has a disposition, including containers, workspaces, empty placeholders,
  creative assets, external/collaborator-owned work, and independent utilities.
- Every migration preserves a source fingerprint and records what was ported, rebuilt, wrapped,
  retained, or rejected.
- Every retirement waits for output/behavior parity and a recovery decision.
- Shared code is promoted only after two real consumers prove the shared boundary.

## Recovery Standard

The adopted target is 9/10 recovery of valuable functionality, governed by
[`RECOVERY-STANDARD.md`](RECOVERY-STANDARD.md) and its machine-readable policy. A completed analysis
milestone is not a recovered runtime; a prototype is not parity; parity is not adoption; and
adoption is not convergence. Every important capability must eventually be ported, shown already
covered, retained independently, rejected, preserved as history, or deferred with an observable
trigger.

Flagship suites target 9/10, production systems target 8/10, and labs target 7/10 until authentic
use earns more investment. The portfolio does not pursue 10/10 reproduction of obsolete or
duplicated behavior.

## What It Is Not

- It is not a giant monolith that absorbs every repo.
- It is not a renamed archive or a folder of symlinks presented as consolidation.
- It is not authority to delete, publish, deploy, push, commit, or alter collaborator-owned work.

## Connection to the Universe

The suites make the existing Cyborg ecosystem, accessibility tools, knowledge systems, creative
pipelines, experiments, and investigation tools cooperate without erasing their histories. The
Cyborg manual remains canonical for cross-system policy. Existing repositories remain sources and,
where appropriate, separately runnable components.

## Production Window

Work proceeds in reviewable waves. A wave must fit one focused implementation session, leave a
machine-checkable result, and end with the next smallest migration named. Large component ports may
span multiple waves, but each wave must preserve a runnable state.

## Operator and System Roles

### Ryan — Owner and final approver

- Core want: useful systems without losing control or drowning in maintenance.
- Default behavior under pressure: needs the next move to be obvious and reversible.
- Voice example: “Rip off the bandaid step by step.”
- Must never be forced into approving hidden publication, deletion, credentials, or irreversible
  consolidation.

### Suite Steward — portfolio integrator

- Core want: one owned contract for each durable capability.
- Default behavior under pressure: stop, preserve evidence, reduce scope, and restore a green gate.
- Voice example: “This source is preserved; this behavior is not yet at parity.”
- Must never convert inference, scaffolding, or a passing narrow test into a completion claim.

### Evidence Keeper — provenance and verification role

- Core want: make every important claim reproducible.
- Default behavior under pressure: retain inputs, versions, outputs, failures, and human decisions.
- Voice example: “The build passed; manual assistive-technology review is still unknown.”
- Must never flatten deterministic, AI-assisted, and manual evidence into one status.
- Must never let a receipt's status name an outcome its gate did not perform; where the work falls
  short of the wave's acceptance boundary, the receipt says which part is still outstanding.

## Craft Rules

1. Always preserve the path back to the source.
2. Never create a new platform where a contract, adapter, pack, or skill is enough.
3. A suite boundary is defined by a user promise and shared state—not a folder name.
4. The emotional rule is relief through trustworthy recovery: interrupted work can resume without
   reconstructing the whole context.
5. When the generic capability is chat-native, keep only the durable state, evidence, UX, corpus,
   or real-world execution that makes the product matter.
